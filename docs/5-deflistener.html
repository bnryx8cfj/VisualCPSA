5.1 Purpose

The deflistener declaration introduces a listener strand into a CPSA skeleton. A listener is an analysis construct used to determine whether a specified term can be received within a realized execution.

Unlike protocol roles defined with defrole, a listener is not an honest participant and does not model protocol behavior. Instead, it expresses an observational requirement that becomes part of the analysis problem.

Typical uses include:

  • Secrecy analysis
  • Confidentiality verification
  • Message reachability analysis
  • Disclosure analysis
  • Derivability analysis
  • Adversary knowledge exploration
  • Attack confirmation
  • Shape refinement

5.2 Relationship to Strand-Space Theory

Within strand-space semantics a listener is represented as a specialized strand.

The listener contains a receive event for the target term:

trace(listener) = < -T >

where:

  • T is the target term
  • - denotes message reception

Associated strand-space concepts include:

  • Event
  • ReceiveEvent
  • Node
  • Strand
  • Skeleton
  • Bundle
  • Shape
  • RealizedExecution

The successful realization of a listener demonstrates that the target term is obtainable within an execution satisfying all protocol assumptions and skeleton constraints.

5.7 Formal Semantics

Given:

(deflistener T)

CPSA constructs a listener strand L such that:

trace(L) = < -T >

The resulting structure contains:

1 Listener
1 Strand
1 Node
1 ReceiveEvent
1 Term Reference

The term becomes an analysis objective.

5.8 Processing Semantics

When CPSA processes a listener declaration:

  1. Parse the target term.
  2. Validate term well-formedness.
  3. Create a Listener instance.
  4. Create a corresponding Strand instance.
  5. Create a ReceiveEvent.
  6. Create a Node representing the reception.
  7. Associate the node with the receive event.
  8. Add the listener to the Skeleton.
  9. Extend the skeleton constraint set.
  10. Search for realized executions.
  11. Generate compatible bundles.
  12. Generate shapes satisfying all constraints.

Possible outcomes:

  • Realized listener
  • Unrealizable listener
  • Additional protocol assumptions required
  • Discovery of attacks or message exposure

5.16 Common Modeling Errors

  1. Treating a listener as a protocol participant.
  2. Using listeners instead of goals.
  3. Using ill-sorted terms.
  4. Assuming listener realization automatically proves an attack.
  5. Ignoring message-algebra constraints.
