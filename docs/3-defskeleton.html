Chapter 3. defskeleton

CPSA 4 DSL Reference

3.1 Purpose

The defskeleton declaration defines a skeleton, the central CPSA analysis object used to describe an initial, partial view of one or more protocol executions under stated assumptions (Liskov, Ramsdell, Guttman, & Rowe, 2026; MITRE Corporation, 2026a). In CPSA, the analyst supplies this partial execution description, and the tool attempts to enumerate the compatible realized executions, called shapes, that satisfy it (Doghmi, Guttman, & Thayer, 2007; MITRE Corporation, 2026a).

A skeleton may specify initial protocol behavior, known role instances, observed event prefixes, origination assumptions, ordering constraints, state or analysis facts, and the security question to be investigated (Liskov et al., 2026; Ramsdell, 2012). In the strand-space interpretation used by CPSA, a skeleton describes partial regular behavior and possible causal structure that may need to be extended before it corresponds to a complete execution (Doghmi et al., 2007; Thayer Fábrega, Herzog, & Guttman, 1998).

A skeleton commonly provides:

  • Initial protocol behavior, such as the role instance whose local execution is being analyzed (Liskov et al., 2026; Ramsdell, 2012).
  • Known role instances, represented in CPSA syntax by strand declarations such as defstrand (Liskov et al., 2026).
  • Observed event prefixes, expressed by the height parameter in a strand instance (Liskov et al., 2026).
  • Assumptions about freshness and compromise, commonly expressed using uniq-orig, uniq-gen, and non-orig forms (Liskov et al., 2026; MITRE Corporation, 2026a).
  • Ordering constraints between nodes, represented by precedence relationships (Doghmi et al., 2007; Liskov et al., 2026).
  • State and fact assertions, represented by forms such as facts and interpreted through CPSA's analysis mechanisms (Liskov et al., 2026).
  • Security query context, especially authentication or secrecy questions encoded as initial behavior and constraints (Doghmi et al., 2007; Ramsdell, 2012).

From a strand-space perspective, a skeleton is a partially ordered representation of regular protocol behavior that CPSA attempts to extend into realized executions and ultimately into minimal realized executions called shapes (Doghmi et al., 2007; Thayer Fábrega et al., 1998).

3.2 Semantics

3.2.1 Conceptual Meaning

A skeleton represents a partially specified strand-space execution rather than a complete run of a protocol (Doghmi et al., 2007; Thayer Fábrega et al., 1998). It records what the analyst assumes or observes, and CPSA searches for the additional regular behavior and causal relationships needed to realize that partial description (Doghmi et al., 2007; Liskov et al., 2026).

The analyst specifies:

  • strands known to exist (Liskov et al., 2026),
  • the amount of each strand observed through a strand height (Liskov et al., 2026),
  • terms assumed to originate uniquely (Liskov et al., 2026; MITRE Corporation, 2026a),
  • terms assumed not to originate, such as uncompromised long-term private keys (Liskov et al., 2026),
  • node ordering relationships (Doghmi et al., 2007; Liskov et al., 2026),
  • additional facts and analysis constraints (Liskov et al., 2026).

CPSA then determines:

  1. Whether the skeleton is satisfiable under the protocol and algebraic assumptions (Liskov et al., 2026).
  2. Which additional behavior must exist for the execution to be realized (Doghmi et al., 2007; Liskov et al., 2026).
  3. Which protocol participants or role instances must be present (Doghmi et al., 2007; Ramsdell, 2012).
  4. Which messages must have been transmitted or received to satisfy causal dependencies (Doghmi et al., 2007; Thayer Fábrega et al., 1998).
  5. Which authentication or secrecy conclusions follow from all compatible shapes (Doghmi et al., 2007; MITRE Corporation, 2026a).
  6. Which protocol shapes satisfy the skeleton (Doghmi et al., 2007; MITRE Corporation, 2026a).

3.2.2 Strand-Space Interpretation

Within strand-space theory, CPSA syntax maps naturally to strand-space concepts because CPSA was developed to automate shape enumeration over strand-space skeletons (Doghmi et al., 2007; MITRE Corporation, 2026a).

CPSA Construct Strand-Space Concept
defskeleton Skeleton
defstrand Strand instance
Node ordering Precedence relation
uniq-orig Unique origination
non-orig Non-originating atom
facts Assertion constraints
shape Minimal realized skeleton

A skeleton is not necessarily realized. Additional strands, transmissions, receptions, or causal relationships may be required before the structure corresponds to a complete execution (Doghmi et al., 2007; Liskov et al., 2026). In CPSA terminology, a realized skeleton is one that contains enough regular behavior to account for its receptions, and a shape is a minimal realized skeleton satisfying the initial behavior (Doghmi et al., 2007; MITRE Corporation, 2026a).

3.3 Abstract Syntax

3.3.1 Declaration Form

(defskeleton protocol-name

  skeleton-component*

)

The protocol-name must reference a protocol already defined using defprotocol; this reflects the fact that a skeleton is interpreted relative to the role definitions and algebra declared by a protocol (Liskov et al., 2026).

3.3.2 General Structure

(defskeleton protocol-name

  (vars ...)

  (defstrand ...)

  (deflistener ...)

  (precedes ...)

  (non-orig ...)

  (uniq-orig ...)

  (uniq-gen ...)

  (facts ...)

  (operation ...)

)

Not all subordinate forms are required in every skeleton; a CPSA input skeleton contains only the declarations needed to encode the initial behavior, assumptions, and query being analyzed (Liskov et al., 2026; Ramsdell, 2012).

3.4 Syntax Elements

3.4.1 Protocol Reference

The protocol reference identifies the protocol whose role definitions are used by the skeleton (Liskov et al., 2026).

Example

(defskeleton ns
  ...
)

Constraints

  • The name must reference an existing protocol in the CPSA input file or environment (Liskov et al., 2026).
  • The skeleton is interpreted relative to that protocol's roles and term algebra (Liskov et al., 2026; MITRE Corporation, 2026a).

3.4.2 Variable Declaration

Variables declared in a skeleton are local symbolic names used to parameterize strand instances and constraints (Liskov et al., 2026).

Example

(vars
  (a b name)
  (n text)
)

Semantics

Variables allow CPSA to reason symbolically about principals, nonces, keys, and other protocol terms rather than only about concrete ground messages (Liskov et al., 2026; Ramsdell, 2012).

Metamodel Mapping

Grammar Metamodel
vars Variable

3.4.3 defstrand

The defstrand form instantiates a protocol role within the skeleton (Liskov et al., 2026).

Example

(defstrand init 3
  (a alice)
  (b bob)
  (n na)
)

Meaning

This declaration states that an instance of role init exists and is observed through the first three events of the role trace (Liskov et al., 2026). This is a standard CPSA modeling pattern in which a participant's local point of view becomes the initial behavior from which CPSA searches for compatible executions (Ramsdell, 2012; MITRE Corporation, 2026a).

See Chapter 4.

3.4.4 deflistener

The deflistener form creates a listener strand that represents adversary acquisition of a target term (Liskov et al., 2026).

Example

(deflistener n)

Meaning

A listener is commonly used to express a secrecy query: if CPSA can realize a skeleton containing a listener for a term, then the analysis has identified a compatible execution in which the adversary can obtain that term under the modeled assumptions (Liskov et al., 2026; MITRE Corporation, 2026a).

See Chapter 5.

3.4.5 precedes

The precedes form defines node ordering constraints between events in the skeleton (Liskov et al., 2026). In strand-space terms, these constraints contribute to the causal or precedence relation among nodes (Doghmi et al., 2007; Thayer Fábrega et al., 1998).

Example

(precedes
  ((0 1) (1 0))
)

Meaning

This declaration states that node (0 1) must occur before node (1 0) in any execution satisfying the skeleton (Liskov et al., 2026).

Semantic Constraints

The resulting precedence graph:

  • must be acyclic, because cyclic causal orderings cannot describe a valid execution (Doghmi et al., 2007; Thayer Fábrega et al., 1998),
  • must respect the intrinsic ordering of events along each strand (Thayer Fábrega et al., 1998; Liskov et al., 2026),
  • must be realizable together with the protocol roles, messages, and origination assumptions (Doghmi et al., 2007; Liskov et al., 2026).

3.4.6 non-orig

The non-orig form declares atoms that do not originate in any regular or adversary behavior modeled by the skeleton (Liskov et al., 2026).

Example

(non-orig
  (privk a)
  (privk b)
)

Meaning

This declaration is typically used to model uncompromised long-term secrets, such as private keys, by asserting that those atoms are not available as originating values in the execution (Liskov et al., 2026; Ramsdell, 2012).

Common Use

Long-term private keys are frequently modeled using non-orig assumptions when analyzing authentication or secrecy properties under uncompromised-key conditions (Liskov et al., 2026; Ramsdell, 2012).

3.4.7 uniq-orig

The uniq-orig form declares terms that originate at exactly one regular node in the skeleton or in any realized extension of it (Liskov et al., 2026).

Example

(uniq-orig n)

Meaning

The declaration models freshness by requiring that the term have a unique regular origin (Liskov et al., 2026; MITRE Corporation, 2026a).

Typical Terms

  • Nonces (Liskov et al., 2026).
  • Session keys (Ramsdell, 2012; Liskov et al., 2026).
  • Fresh identifiers or protocol-specific values (Liskov et al., 2026).

3.4.8 uniq-gen

The uniq-gen form records unique generation assumptions, particularly for analyses involving algebraic structures such as Diffie-Hellman (Liskov et al., 2026).

Example

(uniq-gen x)

Meaning

A uniquely generated value is treated as generated uniquely and may participate in algebraic reasoning according to the algebra selected for the protocol (Liskov et al., 2026).

Common Use

uniq-gen is common in Diffie-Hellman analyses because such analyses require reasoning about generated exponents and related algebraic terms (Liskov et al., 2026).

3.4.9 facts

The facts form associates analysis facts with a skeleton (Liskov et al., 2026).

Example

(facts
  (compromised alice)
  (trusted bob)
)

Semantics

Facts are predicates used by CPSA rules and reasoning procedures to express additional assumptions or derived conditions in the analysis (Liskov et al., 2026).

3.4.10 operation

Operation annotations may appear in CPSA output skeletons to record how CPSA expanded or transformed the search state (Liskov et al., 2026).

Purpose

Operation annotations help explain analysis steps such as test solving, listener introduction, strand augmentation, or other transformations performed during shape enumeration (Liskov et al., 2026; Doghmi et al., 2007).

Examples

  • nonce test (Doghmi et al., 2007; Liskov et al., 2026),
  • encryption test (Doghmi et al., 2007; Liskov et al., 2026),
  • listener introduction (Liskov et al., 2026),
  • strand augmentation (Doghmi et al., 2007; Liskov et al., 2026).

These constructs primarily appear in generated analyses rather than in hand-written input skeletons (Liskov et al., 2026).

3.7 Reference Relationships

Protocol Reference

Skeleton -> Protocol

Multiplicity:

1 Skeleton -> 1 Protocol

Meaning:

Every skeleton is defined with respect to exactly one referenced protocol, because CPSA must resolve the skeleton's role names, variables, and message algebra against a protocol definition (Liskov et al., 2026).

Strand Reference

Skeleton -> Strand

Multiplicity:

1 Skeleton -> 0..* Strands

Meaning:

A skeleton may contain any number of strand instances, depending on the observed behavior and assumptions supplied by the analyst (Liskov et al., 2026; Ramsdell, 2012).

3.8 Cardinality Constraints

Required Constraints

The following constraints are expressed in OCL-like notation as a metamodel interpretation of CPSA's skeleton requirements. They summarize semantic expectations derived from CPSA's documented treatment of skeletons, origination, precedence, and realization (Doghmi et al., 2007; Liskov et al., 2026).

C1

context Skeleton
inv:
self.protocol <> null

A skeleton must reference a protocol so CPSA can interpret strands, roles, and terms in the correct modeling context (Liskov et al., 2026).

C2

context Skeleton
inv:
  self.strands->size() > 0
    or
  self.listeners->size() > 0

A meaningful analysis skeleton normally contains at least one observed regular strand or listener goal, because CPSA starts from initial behavior and searches for compatible shapes (Ramsdell, 2012; MITRE Corporation, 2026a).

C3

context Skeleton
inv:
  self.precedenceGraph.isAcyclic()

The precedence relation must be acyclic, since causal ordering in strand spaces cannot require an event to precede itself through a cycle (Doghmi et al., 2007; Thayer Fábrega et al., 1998).

C4

context Skeleton
inv:
  self.uniqOrigTerms->forAll(t |
    t.originNodes->size() = 1)

Unique origination asserts that a term has exactly one regular origin, which is how CPSA models many freshness assumptions (Liskov et al., 2026).

C5

context Skeleton
inv:
  self.nonOrigTerms
    ->intersection(self.uniqOrigTerms)
    ->isEmpty()

A term cannot consistently be both non-originating and uniquely originating in the same skeleton, because those assumptions assign incompatible origination statuses (Liskov et al., 2026; Doghmi et al., 2007).

3.9 CPSA Processing Semantics

When CPSA encounters a defskeleton declaration, it parses the skeleton, resolves its protocol reference, and uses the initial behavior and constraints to guide shape enumeration (Liskov et al., 2026; MITRE Corporation, 2026a). At a high level, CPSA performs the following conceptual steps:

  1. Parse the skeleton (Liskov et al., 2026).
  2. Resolve protocol references (Liskov et al., 2026).
  3. Instantiate role strands from defstrand forms (Liskov et al., 2026).
  4. Apply variable substitutions and term constraints (Liskov et al., 2026).
  5. Construct the initial strand-space skeleton (Doghmi et al., 2007; Liskov et al., 2026).
  6. Validate origination constraints (Liskov et al., 2026).
  7. Validate ordering constraints (Doghmi et al., 2007; Liskov et al., 2026).
  8. Search for unrealized nodes or unexplained receptions (Doghmi et al., 2007; Liskov et al., 2026).
  9. Introduce required strands when solving authentication tests (Doghmi et al., 2007).
  10. Solve authentication tests that identify necessary causal structure (Doghmi et al., 2007; Thayer Fábrega et al., 1998).
  11. Generate realized skeletons (Doghmi et al., 2007; MITRE Corporation, 2026a).
  12. Minimize realized executions to obtain shapes (Doghmi et al., 2007; MITRE Corporation, 2026a).
  13. Produce shapes compatible with the original skeleton (Doghmi et al., 2007; MITRE Corporation, 2026a).
  14. Generate shape-analysis sentences and goals where applicable (Liskov et al., 2026; MITRE Corporation, 2026a).

3.10 Common Modeling Mistakes

Mistake 1: Missing Freshness Assumptions

Incorrect:

(defskeleton ns
  ...
)

If a value is intended to be fresh, the skeleton should state the corresponding unique-origination assumption; otherwise, CPSA may consider executions inconsistent with the intended modeling scenario (Liskov et al., 2026; Ramsdell, 2012).

Correct:

(uniq-orig n)

Mistake 2: Compromised Key Not Specified

Failing to specify an uncompromised-key assumption such as:

(non-orig (privk a))

may allow analyses in which the adversary can possess or use a key that the analyst intended to model as uncompromised (Liskov et al., 2026; Ramsdell, 2012).

Mistake 3: Inconsistent Ordering Constraints

Incorrect:

(precedes
  ((0 1) (1 0))
  ((1 0) (0 1))
)

This creates a cycle in the precedence relation. Cyclic precedence is incompatible with the event-ordering interpretation of strand spaces (Doghmi et al., 2007; Thayer Fábrega et al., 1998).

Mistake 4: Over-Constrained Skeletons

Too many assumptions can eliminate valid protocol behaviors and may prevent CPSA from revealing attacks or anomalies that would otherwise be compatible with the protocol (Doghmi et al., 2007; MITRE Corporation, 2026a).

Mistake 5: Under-Constrained Skeletons

Insufficient assumptions may produce many shapes, unrealistic executions, or results that do not match the intended security question (Liskov et al., 2026; Ramsdell, 2012).

3.14 Complete Example 1: Authentication Query

The following example is inspired by the Needham-Schroeder public-key lineage of examples commonly used in CPSA and strand-space discussions of authentication. It is not a direct quotation from the CPSA manual; it paraphrases the common CPSA modeling pattern in which one participant's observed role prefix is used as the initial skeleton for shape analysis (Ramsdell, 2012; Thayer Fábrega et al., 1998).

(defskeleton ns

  (vars
    (a b name)
    (n1 text))

  (defstrand resp 2
    (a a)
    (b b)
    (n1 n1))

  (non-orig
    (privk a)
    (privk b))

  (uniq-orig
    n1))

Intent

Determine what additional protocol behavior must exist if a responder has executed the first two events of the responder role. This style of authentication query is typical of CPSA analyses: a skeleton encodes an observed participant viewpoint, and CPSA derives the compatible realized executions and shapes that explain it (Doghmi et al., 2007; Ramsdell, 2012).

Citation and Adaptation Note

This example is adapted in structure from CPSA tutorial practice and from the strand-space tradition of analyzing Needham-Schroeder-style authentication scenarios. The code is newly written for this reference, but the modeling strategy is based on documented CPSA analysis workflows and strand-space authentication reasoning (Ramsdell, 2012; Thayer Fábrega et al., 1998).

3.15 Complete Example 2: Secrecy Analysis

The following example illustrates the standard listener-based pattern for asking whether an adversary can learn a fresh term. This use of listeners is a CPSA modeling technique documented in CPSA materials and consistent with the broader shape-analysis view that secrecy questions can be read from compatible executions (Liskov et al., 2026; MITRE Corporation, 2026a).

(defskeleton ns

  (vars
    (n1 text))

  (deflistener n1)

  (uniq-orig n1))

Intent

Determine whether the adversary can learn a freshly generated nonce. If CPSA finds a realized skeleton compatible with the listener and freshness assumption, the result indicates a modeled execution in which the term can be disclosed; if no such realized skeleton exists, the analysis supports a secrecy conclusion under the stated assumptions (Liskov et al., 2026; Doghmi et al., 2007).

Citation and Adaptation Note

This example is inspired by CPSA documentation and tutorial descriptions of secrecy analysis using listener strands. The specific variable names and minimal skeleton are authored for this reference, but the pattern follows CPSA's documented use of listeners to represent adversary acquisition goals (Liskov et al., 2026; MITRE Corporation, 2026a).

3.16 Complete Example 3: Mixed Strand and Listener Analysis

The following example combines a regular strand with a listener to analyze whether a freshly generated value can be learned by the adversary in the presence of uncompromised long-term private keys. This mixed pattern reflects common CPSA usage in which authentication context and secrecy objectives are represented in the same skeleton (Liskov et al., 2026; Ramsdell, 2012).

(defskeleton simple

  (vars
    (a b name)
    (s text))

  (defstrand init 3
    (a a)
    (b b)
    (s s))

  (deflistener s)

  (uniq-orig s)

  (non-orig
    (privk a)
    (privk b)))

Intent

Analyze secrecy of a uniquely originating value under uncompromised-key assumptions. The regular strand supplies participant behavior, the listener supplies the disclosure objective, uniq-orig models freshness, and non-orig models uncompromised private keys (Liskov et al., 2026; Ramsdell, 2012).

Citation and Adaptation Note

This example is newly written for this reference but is inspired by CPSA documentation and research examples that combine participant strands, listeners, unique origination, and non-originating key assumptions to study secrecy and authentication properties (Doghmi et al., 2007; Liskov et al., 2026).
