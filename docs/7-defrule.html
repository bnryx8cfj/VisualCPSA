Chapter 7. defrule

7.1 Purpose

The defrule declaration defines logical inference rules that extend CPSA protocol analysis with additional semantic knowledge, state-transition constraints, environmental assumptions, trust relationships, and domain-specific reasoning.

Where protocol roles describe participant behavior, rules describe logical relationships that must hold during analysis. Rules enable CPSA to derive additional information from existing observations and constraints.

Typical uses include:

  • Modeling stateful protocols.
  • Expressing protocol invariants.
  • Capturing environmental assumptions.
  • Defining trust relationships.
  • Supporting state transition systems.
  • Constraining execution spaces.
  • Deriving new analysis facts.
  • Supporting rely-guarantee reasoning.

7.2 Semantics

7.2.1 Conceptual Meaning

A defrule declaration introduces a named logical inference rule into the analysis environment.

A rule consists of:

  1. A rule identifier.
  2. Variable declarations.
  3. Antecedent conditions (premises).
  4. Consequent conditions (conclusions).

Conceptually:

If Antecedent Holds
Then Consequent Must Hold

A rule does not describe protocol execution behavior.

Rather, it defines logical implications that CPSA may use while constructing realized executions, shapes, and analysis results.

7.2.2 Analysis Role

Rules participate in:

  • Fact propagation
  • State reasoning
  • Skeleton realization
  • Constraint propagation
  • Shape generation
  • Goal evaluation
  • Derived fact generation

Rules belong primarily to the Analysis Layer of the CPSA metamodel.

7.4 Syntax

7.4.1 Abstract Syntax

(defrule rule-name
  (vars ...)
  antecedent-formula
  consequent-formula)

Every rule contains:

  • Rule name
  • Variable declarations
  • Premise specification
  • Conclusion specification

7.4.2 Syntax Elements

Rule Name

The name uniquely identifies the rule within the enclosing protocol.

Example:

(defrule state-transition
  ...)

Variable Block

Variables used by the rule are declared in a variable block.

Example:

(vars
  (a b name)
  (n text))

Variables are scoped to the rule.

Antecedent

The antecedent specifies conditions that must already hold.

Examples include:

  • Facts
  • Predicates
  • Strand references
  • Node references
  • Ordering constraints
  • Message term relationships

Consequent

The consequent specifies information that may be inferred.

Examples include:

  • New facts
  • Additional predicates
  • Ordering constraints
  • State assertions
  • Derived analysis relationships

7.5 Purpose within CPSA Analysis

Unlike protocol roles, rules do not generate protocol events.

Instead, they:

  • Restrict admissible executions.
  • Introduce semantic assumptions.
  • Provide state transition semantics.
  • Define derived facts.
  • Assist realization reasoning.

Rules therefore augment the protocol interpretation rather than defining protocol behavior itself.

7.11 CPSA Processing Semantics

Rules are evaluated after protocol structures have been parsed and instantiated.

A simplified processing sequence is:

  1. Parse protocol.
  2. Parse roles.
  3. Parse rules.
  4. Parse skeleton.
  5. Construct analysis structures.
  6. Evaluate rule premises.
  7. Apply rule conclusions.
  8. Propagate constraints.
  9. Attempt realization.
  10. Generate shapes.
  11. Evaluate goals.

Rule evaluation may:

  • Derive new facts.
  • Introduce additional constraints.
  • Eliminate infeasible executions.
  • Establish state transitions.
  • Support authentication and state reasoning.

Rules do not replace trace semantics.

Instead, they extend the semantic interpretation of protocol executions.

7.12 Interaction with State Modeling

Rules play a central role in CPSA state reasoning.

Typical pattern:

Observed Fact
      ↓
Rule Application
      ↓
Derived Fact
      ↓
Additional Constraint
      ↓
Further Analysis

Common applications include:

  • Mutable state
  • Authorization systems
  • Capability systems
  • Trust management
  • State transition systems
  • Rely-guarantee reasoning

7.13 Common Modeling Mistakes

Mistake 1: Describing Protocol Behavior

Incorrect:

Using a rule to define message flow.

Correct:

Use defrole traces for protocol behavior.

Mistake 2: Undeclared Variables

Incorrect:

Referencing variables not declared in the rule.

Correct:

Declare all rule variables using vars.

Mistake 3: Encoding Send/Receive Logic

Incorrect:

Using rules to model communication events.

Correct:

Use trace events within roles.

Mistake 4: Circular Derivations

Incorrect:

Creating inference cycles that continuously derive one another.

Correct:

Create acyclic logical relationships whenever possible.

Mistake 5: Confusing Goals and Rules

Incorrect:

Encoding a required security property as a rule.

Correct:

Model security requirements using defgoal.

Use rules only for inference and constraints.

(defprotocol example basic

    (vars (n text))
    ...))
