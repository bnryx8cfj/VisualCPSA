Chapter 6. defgoal

6.1 Introduction

The defgoal declaration is the primary CPSA language construct used to specify formal security properties that a protocol is expected to satisfy. Whereas defprotocol defines a protocol, defrole defines participant behavior within that protocol, and defskeleton defines assumptions about a class of executions, defgoal defines logical properties that should hold across protocol executions consistent with CPSA analysis. (Guttman & Ramsdell, 2020; Ramsdell, 2015). 【1-010047】【2-b546be】

Within CPSA, protocol verification is performed by generating and analyzing protocol shapes. A security goal serves as a formally stated requirement against which those shapes may be evaluated. The purpose of a goal is therefore not to describe behavior, but rather to describe desired security properties that characterize correct behavior. (Guttman & Ramsdell, 2020). 【1-010047】

The CPSA goal language is based on many-sorted first-order logic and supports quantification, implication, conjunction, disjunction, negation, equality, and protocol-specific predicates. These constructs allow protocol designers to express authentication requirements, secrecy requirements, agreement properties, correspondence properties, and protocol-specific invariants. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【2-b546be】【1-010047】

Goals occupy a central role within CPSA because they bridge protocol modeling and protocol verification. A protocol specification defines possible executions, whereas goals define the security requirements those executions should satisfy. Protocol correctness is therefore evaluated with respect to specified goals rather than protocol execution alone. (Guttman & Ramsdell, 2020; MITRE Corporation, 2026). 【1-010047】【3-e03bec】

6.2 Purpose

The purpose of a defgoal declaration is to formally express a security property that can be evaluated against protocol executions produced by CPSA shape analysis. Unlike protocol definitions, which describe behavior, goals define required properties of that behavior. (Guttman & Ramsdell, 2020). 【1-010047】

More specifically, goals are used to:

  1. Specify authentication requirements. (Guttman et al., 2000; Guttman, 2000). 【1-010047】【2-b546be】
  2. Specify secrecy requirements. (Guttman & Ramsdell, 2020; Ramsdell, 2015). 【1-010047】【2-b546be】
  3. Specify agreement properties among protocol participants. (Woo & Lam, 1993; Guttman et al., 2000).
  4. Specify correspondence assertions between protocol events. (Guttman, 2000; Ramsdell, 2015).
  5. Specify protocol-wide invariants. (Guttman & Ramsdell, 2020). 【1-010047】
  6. Provide machine-checkable security requirements. (MITRE Corporation, 2026; Guttman & Ramsdell, 2020). 【3-e03bec】【1-010047】
  7. Enable automated verification through shape analysis. (MITRE Corporation, 2026). 【3-e03bec】

The practical value of CPSA security goals is that they allow protocol designers to formulate security expectations independently of any particular execution. CPSA can then determine whether those expectations are consistent with all protocol shapes generated during analysis. (Guttman & Ramsdell, 2020). 【1-010047】

6.3 Position Within the CPSA DSL

The defgoal declaration belongs to the logical reasoning layer of the CPSA DSL. While the protocol layer defines protocol structure and the analysis layer defines execution hypotheses, the goal layer defines security properties to be verified. (Guttman & Ramsdell, 2020). 【1-010047】

Relationship to Other Top-Level Declarations

Relationship to defprotocol

A goal is always associated with a protocol. The protocol provides the roles, variables, message structures, and semantics referenced by the goal. Every valid goal therefore exists within the context of a protocol specification. (Guttman & Ramsdell, 2020). 【1-010047】

Relationship to defrole

Goal formulas frequently reference roles using role predicates. These predicates allow goals to reason about the existence and behavior of role instances occurring within protocol executions. (Ramsdell, 2015). 【2-b546be】

Relationship to defskeleton

A skeleton describes assumptions about protocol executions. Goal evaluation ultimately occurs relative to shapes generated from skeleton analysis. Consequently, skeletons provide the execution context in which goals are tested. (Guttman & Ramsdell, 2020; MITRE Corporation, 2026). 【1-010047】【3-e03bec】

Relationship to defstrand

Many goal predicates refer to strands and strand positions. Authentication goals, for example, commonly assert that the existence of one strand implies the existence of another corresponding strand. (Guttman et al., 2000; Ramsdell, 2015). 【2-b546be】【1-010047】

Relationship to deflistener

Listener strands represent adversarial observation of messages. Shape satisfaction of secrecy goals may depend upon whether a listener strand can be derived within a realized execution. (Guttman & Ramsdell, 2020). 【1-010047】

Relationship to defrule

Rules constrain or extend analysis by introducing additional semantic assumptions. These assumptions may influence the set of realizable executions and therefore affect goal satisfaction. (Guttman & Ramsdell, 2020). 【1-010047】

6.7 Abstract Syntax

The most general form of a goal declaration is:

(defgoal protocol-name
  formula)

The declaration consists of the keyword defgoal, the name of the protocol to which the goal applies, and a logical formula expressing the desired security property. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【2-b546be】【1-010047】

In practice, CPSA goals are usually expressed as quantified implications:

(defgoal protocol-name
  (forall (...)
    (implies
      antecedent
      consequent)))

This structure reflects the dominant usage pattern in CPSA authentication and secrecy reasoning, where the antecedent identifies an observed execution condition and the consequent identifies a required execution property. (Guttman & Ramsdell, 2020). 【1-010047】

Conceptually:

Observation
      ↓
 Antecedent
      ↓
  Implies
      ↓
 Consequence

A protocol satisfies the goal only when every execution satisfying the antecedent also satisfies the consequent. (Ramsdell, 2015). 【2-b546be】

6.8 Concrete Syntax

Overview

The CPSA goal language is a many-sorted first-order logical language. It supports variable declarations, quantification, implication, conjunction, disjunction, negation, equality, and protocol-specific predicates. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【2-b546be】【1-010047】

Canonical Grammar

GoalDeclaration ::=
    (defgoal ProtocolName Formula)

Formula ::=
      Predicate
    | (forall VariableList Formula)
    | (exists VariableList Formula)
    | (implies Formula Formula)
    | (and Formula*)
    | (or Formula*)
    | (not Formula)

VariableList ::=
    ((Variable Sort)*)

Predicate ::=
      p
    | non
    | uniq
    | uniq-at
    | fact
    | prec
    | =

The grammar is recursive because formulas may contain nested formulas. This permits construction of arbitrarily complex logical sentences while preserving a uniform abstract syntax. (Ramsdell, 2015). 【2-b546be】

Variable Declarations

Variables are declared using CPSA sorts.

Example:

((a name)
 (b name)
 (n text)
 (z strd))

In this example:

  • a is a name.
  • b is a name.
  • n is a text value.
  • z is a strand identifier.

Variables must be declared before use. Undeclared variables are invalid and constitute a semantic error. (Ramsdell, 2015). 【2-b546be】

Quantified Formulas

Universal quantification:

(forall
   ((a name)
    (b name))
   formula)

Existential quantification:

(exists
   ((z strd))
   formula)

Universal quantification is generally used to define security requirements, while existential quantification is commonly used to establish the existence of authentication witnesses. (Guttman & Ramsdell, 2020; Ramsdell, 2015). 【1-010047】【2-b546be】

Implication Formulas

(implies
   antecedent
   consequent)

Implication expresses the fundamental structure of most CPSA security properties: if certain protocol conditions are observed, then additional security-relevant conditions must also hold. (Guttman & Ramsdell, 2020). 【1-010047】

Compound Formulas

Conjunction:

(and A B C)

Disjunction:

(or A B)

Negation:

(not A)

These operators allow construction of complex logical expressions describing authentication, secrecy, and protocol correctness requirements. (Ramsdell, 2015). 【2-b546be】

6.9 Semantic Interpretation

A defgoal declaration is interpreted over the protocol execution space generated by CPSA shape analysis. CPSA attempts to enumerate all essentially different executions that satisfy a protocol specification and a set of initial assumptions. These essentially different executions are called shapes. Security goals are evaluated against those shapes to determine whether the specified property is satisfied in all relevant executions. (Guttman & Ramsdell, 2020; MITRE Corporation, 2026). 【1-57b8b1】【2-5b9611】

The semantic meaning of a goal is therefore independent of any single protocol run. Instead, a goal is evaluated with respect to an entire class of executions represented by CPSA's shape analysis. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Conceptually:

Protocol
   ↓
Analysis Assumptions
   ↓
Shape Generation
   ↓
Execution Models
   ↓
Goal Evaluation
   ↓
Satisfied or Violated

A goal succeeds when every execution satisfying the antecedent also satisfies the consequent. This corresponds to the standard logical interpretation of implication adopted by CPSA's security-goal framework. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【3-f59424】【1-57b8b1】

Most goals describe a relationship between an observed execution fragment and an execution property that must also hold. In authentication reasoning, for example, an observed participant execution serves as the antecedent, while the existence of a corresponding participant execution forms the consequent. (Guttman et al., 2000; Guttman, 2000).

Semantically:

Antecedent ⇒ Consequent

A violation occurs whenever CPSA discovers a shape satisfying the antecedent but not satisfying the consequent. Such a shape represents a counterexample to the security property being specified. (Guttman & Ramsdell, 2020). 【1-57b8b1】

6.10 Quantification

Quantification provides the mechanism by which goals express properties over protocol participants, strands, messages, and other protocol entities. CPSA uses many-sorted first-order logic, meaning every variable has an associated sort. (Ramsdell, 2015). 【3-f59424】

Universal Quantification

Syntax

(forall
   ((a name)
    (b name))
   formula)

Semantics

Universal quantification states that the enclosed formula must hold for every assignment of values consistent with the declared sorts. (Ramsdell, 2015). 【3-f59424】

Mathematically:

∀x F(x)

Universal quantification is commonly used to express security guarantees.

Example:

(forall
   ((z strd))
   formula)

Meaning:

For every strand z, the enclosed property must hold.

Authentication goals almost always begin with a universally quantified formula because they describe requirements that must hold for every qualifying execution. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Existential Quantification

Syntax

(exists
   ((z strd))
   formula)

Semantics

Existential quantification states that there exists at least one assignment satisfying the enclosed formula. (Ramsdell, 2015). 【3-f59424】

Mathematically:

∃x F(x)

Existential quantification is frequently used to express authentication witnesses.

Example:

(exists
   ((z strd))
   (p "resp" z 2))

Meaning:

There exists a responder strand that has reached position 2.

Authentication goals typically include an existential consequent asserting the existence of another participant execution. (Guttman et al., 2000; Guttman, 2000).

6.11 Logical Operators

The CPSA goal language includes a small but expressive collection of logical operators. These operators are sufficient to express the authentication and secrecy properties typically required for symbolic protocol analysis. (Ramsdell, 2015). 【3-f59424】

Implication

Syntax

(implies A B)

Semantics

Implication expresses a conditional security property.

Formally:

A ⇒ B

Meaning:

If A is true, then B must also be true.

Implication forms the basis of nearly all CPSA authentication goals because it provides a way to express security requirements as conditional guarantees. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Conjunction

Syntax

(and A B C)

Semantics

Conjunction requires all enclosed formulas to evaluate to true.

Formally:

A ∧ B ∧ C

Conjunction is commonly used to specify execution assumptions, participant assumptions, freshness assumptions, and key assumptions simultaneously. (Ramsdell, 2015). 【3-f59424】

Disjunction

Syntax

(or A B)

Semantics

Disjunction requires at least one enclosed formula to evaluate to true.

Formally:

A ∨ B

Disjunction is less common than conjunction in CPSA security goals but remains useful for expressing alternative protocol behaviors. (Ramsdell, 2015). 【3-f59424】

Negation

Syntax

(not A)

Semantics

Negation requires the enclosed formula to evaluate to false.

Formally:

¬A

Negation is used primarily in secrecy reasoning and in the specification of protocol constraints. (Guttman & Ramsdell, 2020). 【1-57b8b1】

6.12 Goal Predicates

Predicates constitute the atomic building blocks of CPSA goal formulas. They allow formulas to reference protocol roles, variables, execution properties, and analysis assumptions. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【3-f59424】【1-57b8b1】

Role Progress Predicate

Syntax

(p "init" z 3)

Meaning

The strand identified by z has progressed through position 3 of role init.

This predicate is one of the most commonly used goal predicates because authentication goals often reason about completed or partially completed role executions. (Ramsdell, 2015). 【3-f59424】

Role Parameter Predicate

Syntax

(p "init" "a" z a)

Meaning

Role parameter a in strand z is bound to the value represented by term a.

Parameter predicates are used extensively in agreement and authentication goals because they permit comparison of values across multiple strands. (Guttman et al., 2000).

Non-Originating Predicate

Syntax

(non k)

Meaning

Term k is assumed not to originate during execution.

Examples:

(non (privk a))

(non (privk b))

These assumptions commonly represent uncompromised private keys or uncompromised shared secrets. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Unique Origination Predicate

Syntax

(uniq n)

Meaning

Term n originates at exactly one point in the execution.

Typical uses include:

  • Nonces
  • Session keys
  • Fresh random values

Unique origination assumptions are central to many authentication proofs because they provide evidence that specific message values originated from a unique source. (Guttman, 2000; Guttman et al., 2000).

Fact Predicate

Syntax

(fact f x y)

Meaning

The analysis fact identified by f holds for the supplied arguments.

Fact predicates provide a mechanism for extending protocol reasoning through user-defined analysis facts and rule systems. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Equality Predicate

Syntax

(= x y)

Meaning

Terms x and y are equal.

Equality predicates frequently appear in agreement goals because participant agreement often requires equality of identities, nonces, session keys, or message fields. (Woo & Lam, 1993; Ramsdell, 2015).

Precedence Predicate

Syntax

(prec n1 n2)

Meaning

Node n1 occurs before node n2.

Precedence predicates express temporal and causal ordering constraints within protocol executions. Such constraints are often required when reasoning about authentication and causality. (Thayer, Herzog, & Guttman, 1999; Guttman, 2000).

6.13 Authentication Goals

Authentication goals are the most common use of defgoal. CPSA authentication goals typically express correspondence properties between multiple participant executions. Rather than focusing solely on message receipt, these goals reason about the existence of compatible executions that explain the observed behavior. (Guttman et al., 2000; Guttman, 2000).

General Authentication Pattern

(defgoal protocol-name
  (forall (...)
    (implies
      initiator-observation
      responder-existence)))

The antecedent describes an observed execution state, while the consequent requires evidence of a corresponding participant execution. (Guttman & Ramsdell, 2020). 【1-57b8b1】

Conceptually:

Completed Execution
         ↓
     Observed
         ↓
     Requires
         ↓
 Matching Execution

This structure captures the central idea of authentication in strand-space analysis:

If one participant has completed an execution under specified assumptions, another participant must have performed a corresponding execution. (Guttman et al., 2000; Thayer et al., 1999).

Authentication Witnesses

Authentication goals typically use existential quantification to specify witnesses.

Example:

(exists
   ((z2 strd))
   witness-formula)

The witness strand provides evidence that another legitimate participant execution occurred. (Guttman et al., 2000).

Strong and Weak Authentication

Authentication goals can express varying strengths of assurance.

Weak authentication may require only existence of a corresponding execution.

Stronger authentication may additionally require:

  • Agreement on identities.
  • Agreement on nonces.
  • Agreement on session keys.
  • Agreement on protocol parameters.
  • Ordering constraints.

These stronger forms of agreement are often achieved through additional predicates and equality constraints within the consequent. (Woo & Lam, 1993; Guttman et al., 2000).

6.14 Secrecy Goals

Secrecy goals express requirements that protected information remain unavailable to the adversary. In symbolic protocol analysis this generally means that a protected term cannot be derived by the adversarial capabilities represented within the protocol model. (Guttman & Ramsdell, 2020; Thayer et al., 1999). 【1-57b8b1】

Conceptually:

Protected Value
        ↓
Adversary Cannot Derive
        ↓
   Secrecy Preserved

Secrecy reasoning typically relies upon assumptions such as:

  • Non-originating private keys.
  • Honest participant behavior.
  • Unique origination of fresh values.
  • Correct message encryption.

(Guttman & Ramsdell, 2020). 【1-57b8b1】

Generic Secrecy Pattern

(defgoal protocol-name
  (forall (...)
    (implies
      secrecy-assumptions
      secrecy-property)))

A secrecy violation occurs when CPSA discovers a shape demonstrating that a protected value can become accessible despite the stated assumptions. Such a shape constitutes a counterexample to the secrecy property. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【3-f59424】【1-57b8b1】

6.15 Agreement Goals

Agreement goals require protocol participants to agree on selected protocol values. Agreement properties are often considered stronger forms of authentication because they require more than mere participation; they require consistency of participant beliefs concerning protocol state. (Woo & Lam, 1993; Guttman et al., 2000).

Agreement properties frequently concern:

  • Participant identities
  • Nonces
  • Session keys
  • Fresh values
  • Role parameters

Conceptually:

Participant A
        ↓
 Shared Values
        ↓
Participant B

Agreement goals are usually encoded as authentication goals supplemented by equality predicates.

Example:

(and
   (= a a2)
   (= b b2)
   (= n n2))

Such constraints ensure that corresponding participants agree upon the referenced values. (Woo & Lam, 1993).

6.16 Correspondence Goals

Correspondence goals establish causal relationships between protocol events or executions. The central idea is that occurrence of one event implies occurrence of another event satisfying related conditions. (Guttman, 2000; Ramsdell, 2015). 【3-f59424】

Event A Occurs

6.17 Goal Evaluation Process

CPSA evaluates security goals through a multi-stage analysis workflow that combines logical formula processing with shape generation and verification. The objective of the evaluation process is to determine whether a specified security property is satisfied by every protocol execution represented within the generated shape analysis. (Guttman & Ramsdell, 2020; MITRE Corporation, 2026). 【1-6a7c56】【2-e433cb】

Conceptual Workflow

Goal
 ↓
Parse
 ↓
Resolve Variables
 ↓
Resolve Roles
 ↓
Construct Logical Formula
 ↓
Generate Shapes
 ↓
Evaluate Formula
 ↓
Satisfied / Violated

The workflow demonstrates the relationship between logical security requirements and CPSA's execution-based analysis methodology. Goals are not evaluated directly against protocol syntax; they are evaluated against the set of protocol executions generated through shape analysis. (Guttman & Ramsdell, 2020). 【1-6a7c56】

Processing Semantics

Step 1. Parse Declaration

The defgoal declaration is parsed according to CPSA grammar rules and converted into an internal abstract representation consisting of formulas, predicates, variables, and logical operators. The parser verifies that the declaration conforms to CPSA syntactic requirements before analysis proceeds. (Ramsdell, 2015). 【3-839e84】

Step 2. Validate Variables

Variable declarations are analyzed to ensure:

  • Every variable possesses a valid CPSA sort.
  • Every variable reference corresponds to a declared variable.
  • Quantifier scopes are well formed.
  • Sort usage is semantically consistent.

(Ramsdell, 2015). 【3-839e84】

Examples of valid declarations include:

((a name)
 (b name)
 (n text)
 (z strd))

Undeclared variables or variables used outside their scope constitute semantic errors.

Step 3. Resolve Protocol References

Role names, role parameters, predicates, and protocol identifiers referenced within the goal are resolved against the associated protocol definition.

Validation includes:

  • Role existence checking.
  • Role parameter validation.
  • Predicate reference validation.
  • Protocol consistency verification.

The objective is to ensure that every protocol element referenced by the goal exists within the protocol specification against which the goal is evaluated. (Guttman & Ramsdell, 2020). 【1-6a7c56】

Step 4. Construct Formula Representation

After validation, CPSA constructs an internal logical representation of the goal.

Conceptually:

Goal
 └── UniversalFormula
       └── ImplicationFormula
             ├── Antecedent
             └── Consequent

The resulting formula hierarchy preserves:

  • Quantifier structure
  • Predicate relationships
  • Variable bindings
  • Logical operators

This representation becomes the basis for subsequent logical evaluation. (Ramsdell, 2015). 【3-839e84】

Step 5. Generate Shapes

CPSA performs its protocol-analysis process using the protocol definition and execution assumptions supplied through skeletons, rules, and message-algebra constraints.

The purpose of shape generation is to discover all essentially different protocol executions consistent with the supplied assumptions. CPSA refers to these executions as shapes. As noted by Guttman and Ramsdell, "We call these essentially different executions the shapes of the protocol." (Guttman & Ramsdell, 2020, p. 3). 【1-6a7c56】

Shape generation incorporates:

  • Strand-space semantics
  • Adversary behavior
  • Message-algebra reasoning
  • Causal ordering constraints
  • Protocol-role semantics

(Guttman & Ramsdell, 2020; MITRE Corporation, 2026). 【1-6a7c56】【2-e433cb】

Step 6. Evaluate Goal Satisfaction

The logical formula is evaluated against the generated shapes.

Conceptually:

Generated Shape
       ↓
 Formula Evaluation
       ↓
 True or False

For a universally quantified implication:

∀x (A ⇒ B)

CPSA determines whether every relevant execution satisfying A also satisfies B.

Typical evaluation questions include:

  • Does a corresponding responder strand exist?
  • Are nonce values uniquely originating?
  • Do participants agree on identities?
  • Is a protected value secret?
  • Are required ordering constraints satisfied?

(Guttman & Ramsdell, 2020; Ramsdell, 2015). 【1-6a7c56】【3-839e84】

Step 7. Produce Results

After evaluation, CPSA reports whether the goal is satisfied.

Possible outcomes include:

Goal Satisfied

Every shape satisfying the antecedent also satisfies the consequent.

Conceptually:

All Shapes
      ↓
 Goal Holds
      ↓
 Verified

A satisfied result indicates that no counterexample execution was discovered within the space explored by CPSA. (Guttman & Ramsdell, 2020). 【1-6a7c56】

Goal Violated

At least one shape satisfies the antecedent but violates the consequent.

Conceptually:

Shape
  ↓
Antecedent True
  ↓
Consequent False
  ↓
Counterexample

A violating shape serves as an explicit counterexample demonstrating that the security property does not hold. Such counterexamples frequently reveal protocol flaws, unsafe assumptions, or missing protocol constraints. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【3-839e84】【1-6a7c56】

Goal Underdetermined

In some situations the analysis may indicate that additional assumptions are required before the desired property can be established.

Examples include:

  • Missing freshness assumptions.
  • Missing non-originating assumptions.
  • Missing protocol facts.
  • Insufficient role constraints.

Additional analysis assumptions may produce a stronger set of shapes capable of supporting the desired conclusion. (Guttman & Ramsdell, 2020

6.18 UML Metamodel Specification

The CPSA Goal Package provides the abstract syntax and semantic representation necessary for expressing protocol security requirements. The metamodel captures the structure of goal declarations independently of any concrete CPSA syntax and provides a foundation for UML-based modeling, validation, and tooling. (Ramsdell, 2015; Guttman & Ramsdell, 2020). 【1-f2936c】【2-9d5003】

The metamodel distinguishes between:

  1. Goal declarations.
  2. Logical formulas.
  3. Quantifiers.
  4. Predicates.
  5. Variables.
  6. Message terms.

Each of these concepts possesses distinct semantics and therefore warrants representation as an explicit metamodel element.

6.23 Common Modeling Mistakes

Errors involving goal specifications typically arise from incorrectly scoped variables, incomplete assumptions, or misuse of predicates. (Ramsdell, 2015). 【1-f2936c】

Missing Quantifiers

Incorrect:

(defgoal p
   (implies A B))

Correct:

(defgoal p
   (forall (...)
      (implies A B)))

Reason:

Security properties generally require explicit quantification.

Undeclared Variables

Incorrect:

(p "init" "a" z a)

when a has not been declared.

Reason:

Unbound variables have no defined interpretation.

Undefined Roles

Incorrect:

(p "server" z 3)

if role server does not exist.

Reason:

Goal predicates may reference only roles defined within the associated protocol.

Missing Authentication Witness

Incorrect:

(implies
   initiator-complete
   true)

Reason:

The consequent imposes no authentication requirement and therefore provides no meaningful security guarantee. (Guttman et al., 2000).

Missing Freshness Assumptions

Incorrect:

(implies
   completed-run
   responder-exists)

without any assumptions concerning freshness or unique origination.

Reason:

Authentication claims often depend upon nonce uniqueness or other freshness assumptions. (Guttman, 2000; Guttman et al., 2000).

Incorrect Sort Usage

Incorrect:

(uniq z)

where z is a strand variable.

Reason:

Unique origination applies to message terms rather than strand identifiers.

6.25 Complete Example

The following example is adapted from the Needham-Schroeder Public-Key protocol family and illustrates a typical authentication goal used in CPSA literature. (Guttman & Ramsdell, 2020; UMBC Protocol Analysis Laboratory, 2026). 【2-9d5003】【3-83f9d5】

(defgoal ns
  (forall
      ((a b name)
       (na nb text)
       (z strd))
    (implies
      (and
        (p "init" z 3)
        (p "init" "a" z a)
        (p "init" "b" z b)
        (p "init" "na" z na)
        (p "init" "nb" z nb)
        (uniq na)
        (non (privk a))
        (non (privk b)))
      (exists
          ((z2 strd))
        (and
          (p "resp" z2 2)
          (p "resp" "a" z2 a)
          (p "resp" "b" z2 b)
          (p "resp" "na" z2 na)
          (p "resp" "nb" z2 nb))))))

Interpretation

This goal states that whenever an initiator completes the Needham-Schroeder protocol under the stated assumptions, there must exist a corresponding responder execution that agrees on the participant identities and nonce values. This is a classic strand-space authentication property and exemplifies the authentication-witness pattern commonly used in CPSA analyses. (Guttman et al., 2000; Ramsdell, 2015; UMBC Protocol Analysis Laboratory, 2026). 【2-9d5003】【1-f2936c】【3-83f9d5】

6.27 UML Metamodel Interpretation

Within the canonical CPSA metamodel:

  • Goal is a first-class declaration.
  • Goal belongs to exactly one Protocol.
  • Goal contains exactly one root Formula.
  • Formula forms a recursive logical-expression hierarchy.
  • Predicates provide atomic logical assertions.
  • Variables provide scoped bindings for quantified formulas.
  • Terms provide references into the CPSA message algebra.
  • Goal satisfaction is evaluated over Shapes and RealizedExecutions derived through CPSA analysis. (Guttman & Ramsdell, 2020; Ramsdell, 2015). 【2-9d5003】【1-f2936c】

The Goal Package therefore provides the semantic bridge between protocol definition and protocol verification.
