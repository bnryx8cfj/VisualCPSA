Chapter 1. defprotocol

1.1 Overview

The defprotocol declaration is the root declaration construct used to define a CPSA protocol. A protocol declaration establishes the protocol namespace, selects the message algebra used during symbolic analysis, and serves as the containment context for role definitions and protocol-specific rules. A protocol declaration establishes the context within which CPSA interprets role definitions, protocol rules, and subsequent analysis specifications. (Liskov, Ramsdell, Guttman, & Rowe, 2024; Guttman, Ramsdell, Rowe, & Liskov, 2026)

A protocol definition is the foundational unit from which CPSA constructs its internal protocol model. All role behavior, message traces, variables, assumptions, and protocol-specific inference rules are interpreted within the context established by a defprotocol declaration. CPSA documentation presents protocols as the primary organizational unit used to model participant behavior and support shape analysis. (Liskov et al., 2024; Guttman et al., 2026)

1.2 Purpose

The purpose of defprotocol is to:

  • Assign a unique protocol identifier.
  • Select the protocol algebra.
  • Define the scope in which roles are declared.
  • Define the scope in which protocol-specific rules are declared.
  • Provide the protocol model referenced by skeleton and goal declarations.

These responsibilities correspond to the use of protocol declarations described throughout the CPSA 4 manuals, where protocols provide the structural context for participant roles and analysis inputs. (Liskov et al., 2024; Guttman et al., 2026)

A CPSA model SHALL define protocol behavior using one or more protocol declarations. (Liskov et al., 2024; Guttman et al., 2026)

1.3 CPSA 4 Source Syntax

A protocol declaration begins with the keyword defprotocol followed by a protocol name and algebra identifier. This structure is consistent with the CPSA 4 input language documented in the CPSA manuals and example protocol specifications. (Liskov et al., 2024; Guttman et al., 2026)

1.5 Immediate Child Declarations

The immediate children of a protocol declaration are role and rule declarations. (Liskov et al., 2024; Guttman et al., 2026)

defrole

Roles define participant behavior.

A role specifies:

  • Variables.
  • Message events.
  • Origination assumptions.
  • Non-origination assumptions.
  • Facts.

The role construct is the CPSA mechanism for modeling the local behavior of protocol participants as traces of message events. (Liskov et al., 2024; Guttman et al., 2026)

defrule

Rules define protocol-specific inference behavior.

Rules extend the logical theory available during analysis. (Liskov et al., 2024; Guttman et al., 2026)

1.5.1 Protocol Namespace Semantics

A protocol declaration establishes a namespace that contains protocol-owned declarations. Namespace scoping allows CPSA to distinguish declarations belonging to different protocols contained within the same specification environment. References originating in analysis and goal declarations are resolved through protocol identifiers. (Liskov et al., 2024; Ramsdell, n.d.)

The namespace includes:

  • The protocol identifier.
  • All contained role identifiers.
  • All contained rule identifiers.
  • Protocol-local vocabulary introduced by contained declarations.

The namespace created by a protocol SHALL be used when resolving references originating from protocol, analysis, and goal declarations that reference the protocol by name. (Liskov et al., 2024; Guttman et al., 2026)

Identifiers defined within one protocol SHALL NOT automatically become visible within another protocol. (Liskov et al., 2024; Ramsdell, n.d.)

1.5.2 Protocol Body Ordering Rules

Conceptually, the protocol body consists of protocol-owned declarations interpreted within the protocol namespace. (Liskov et al., 2024; Guttman et al., 2026)

(defprotocol protocol-name algebra
  protocol-body*)

Ordering Independence

The semantic meaning of a protocol derives from its contained declarations and their relationships. CPSA documentation emphasizes protocol content and structure rather than presentation formatting. (Liskov et al., 2024; Guttman et al., 2026)

Recommended Organization

For specification clarity, protocol definitions SHOULD:

  1. Define roles before rules.
  2. Group related participant roles together.
  3. Place protocol constraints and inference rules after participant definitions.

This ordering convention is a documentation recommendation for readability, not a distinct CPSA declaration construct. (Liskov et al., 2024; Guttman et al., 2026)

Example:

(defprotocol example basic

  (defrole initiator
    ...)

  (defrole responder
    ...)

  (defrule authentication-property
    ...))

1.6 Declaration Relationships

Relationship to defrole

A protocol owns one or more role definitions. (Liskov et al., 2024; Guttman et al., 2026)

Multiplicity

Protocol 1 ---- 1..* Role

Ownership

Protocol ◼── Role

Semantics

A role SHALL belong to exactly one protocol.

A role inherits:

  • Protocol algebra.
  • Protocol namespace.
  • Protocol semantic context.

This relationship reflects CPSA's organization of participant-role behavior within protocol declarations. (Liskov et al., 2024; Guttman et al., 2026)

Relationship to defrule

A protocol may own zero or more rules. (Liskov et al., 2024; Guttman et al., 2026)

Multiplicity

Protocol 1 ---- 0..* Rule

Ownership

Protocol ◼── Rule

Semantics

A rule SHALL belong to exactly one protocol.

Rules are interpreted using the algebra and vocabulary defined by the owning protocol. (Liskov et al., 2024; Guttman et al., 2026)

The Protocol metaclass is referenced, but not owned, by analysis and goal declarations. Analysis declarations refer to protocol definitions by identifier. Consequently, a protocol forms the semantic root from which strands, skeletons, listeners, goals, and formulas derive their protocol-specific meaning. (Liskov et al., 2024; Guttman et al., 2026)

The UML metamodel described in this reference is a documentation abstraction intended to make declaration ownership, cardinality, and navigability explicit. 1.9 CPSA Processing Semantics

When CPSA processes a protocol declaration it performs the following conceptual activities:

  1. Parse the protocol identifier.
  2. Resolve the algebra.
  3. Establish the protocol namespace.
  4. Create the protocol model.
  5. Parse all contained role declarations.
  6. Parse all contained rule declarations.
  7. Validate protocol consistency.
  8. Register the protocol for subsequent analysis declarations.

CPSA subsequently analyzes skeletons that reference the protocol and derives shape analyses using the protocol's roles, assumptions, and selected algebra. (Liskov et al., 2024; Guttman et al., 2026)

The resulting protocol model is then referenced by skeleton and goal declarations. (Liskov et al., 2024; Guttman et al., 2026)

1.10 Common Modeling Mistakes

Missing Roles

Protocols without roles do not define participant behavior.

Duplicate Role Names

Role identifiers should be unique within the protocol.

Duplicate Rule Names

Rule identifiers should be unique within the protocol.

Algebra Mismatch

Diffie-Hellman operators should not be used in a protocol declared using the basic algebra.

Protocol Logic Embedded in Skeletons

Reusable protocol assumptions should be modeled as protocol-level rules when appropriate.

These modeling mistakes are expressed here as reference-document guidance derived from the CPSA declaration structure, algebra selection model, and common protocol-modeling patterns described in CPSA documentation. (Liskov et al., 2024; Guttman et al., 2026)

1.11 Example

The following example is inspired by the Needham-Schroeder public-key protocol examples used throughout CPSA documentation. The example is not a verbatim reproduction of CPSA source material but illustrates the same structure of a protocol declaration containing roles and protocol-level reasoning constructs. (Liskov et al., 2024; Guttman et al., 2026)

(defprotocol needham-schroeder basic

  (defrole initiator
    ...)

  (defrole responder
    ...)

  (defrule authentication-invariant
    ...))

In this example:

  • The protocol name is needham-schroeder.
  • The selected algebra is basic.
  • Two roles are declared.
  • One protocol rule is declared.

Needham-Schroeder is frequently used within both CPSA documentation and the protocol-analysis literature because it demonstrates participant-role modeling and provides a well-known case in which automated analysis reveals non-obvious authentication vulnerabilities. (Liskov et al., 2024; Guttman et al., 2026; Lowe, 1996)
