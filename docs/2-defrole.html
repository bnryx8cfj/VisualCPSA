Chapter 2: defrole

2.1 Overview

The defrole declaration defines a protocol role within a CPSA protocol specification. Protocols in CPSA are composed of roles and rules, and role definitions provide the behavioral templates from which execution strands are instantiated during analysis. 【1-65b48d】【2-cf2cc9】

A role models the expected behavior of an honest protocol participant and contains declarations that describe message exchanges, assumptions, variables, and protocol-specific analysis information. 【1-65b48d】【2-cf2cc9】

Within the CPSA semantic domain, a role corresponds to an abstract strand specification consisting of:

  • Variables
  • Message events
  • Ordering constraints
  • Origination assumptions
  • Non-origination assumptions
  • Facts
  • Channel annotations where supported
  • State-related annotations where supported

A role does not represent an execution instance. Instead, it defines a reusable behavioral specification that may be instantiated one or more times as strands during shape analysis. Individual strand instances may subsequently participate in skeletons, bundles, shapes, and realized executions. 【1-65b48d】【3-5768ef】

The distinction between protocol definitions and execution instances is fundamental to CPSA's analytic approach. Protocols define what honest participants are intended to do, whereas CPSA's search procedures determine what executions are compatible with those definitions. 【3-5768ef】【2-cf2cc9】

2.2 Purpose

The purpose of defrole is to:

  1. Define protocol participant behavior. 【1-65b48d】【2-cf2cc9】
  2. Specify ordered message transmission and reception events. 【1-65b48d】【2-cf2cc9】
  3. Declare variables used within protocol messages. 【1-65b48d】【2-cf2cc9】
  4. Express assumptions required for protocol correctness. 【1-65b48d】【2-cf2cc9】
  5. Provide templates for strand instantiation. 【1-65b48d】【2-cf2cc9】
  6. Enable authentication analysis. 【3-5768ef】【2-cf2cc9】
  7. Enable secrecy analysis. 【3-5768ef】【2-cf2cc9】
  8. Support shape generation and protocol exploration. 【3-5768ef】【2-cf2cc9】

Every participant behavior represented in CPSA is described through one or more roles. Typical protocol participants include initiators, responders, trusted servers, certification authorities, registration authorities, directory services, and hardware security devices. 【1-65b48d】【2-cf2cc9】

2.3 Semantic Meaning

A role is a declarative specification of an expected participant behavior. It describes how a participant is intended to behave rather than documenting what has already occurred in an execution. 【1-65b48d】【2-cf2cc9】

Semantically, a role defines:

  • A sequence of protocol events.
  • Parameters represented by variables.
  • Assumptions regarding origination.
  • Assumptions regarding compromise.
  • Optional facts.
  • Optional channel information.
  • Optional state-related annotations.

A role becomes operational only when instantiated as a strand. CPSA analyzes executions by reasoning about strands generated from role definitions and determining what additional behavior must necessarily exist in any execution compatible with the available evidence. 【3-5768ef】【1-65b48d】

A role belongs to the protocol-definition layer, whereas strands, skeletons, bundles, shapes, and realized executions belong to the analysis layer. This separation allows CPSA to distinguish between protocol intent and protocol behavior. 【1-65b48d】【2-cf2cc9】

2.4 Relationship to Strand Space Theory

CPSA is founded on strand-space theory, a formal framework for representing and reasoning about cryptographic protocol executions. In strand-space theory, executions are represented as strands consisting of ordered communication events connected through causal relationships. 【1-65b48d】【2-cf2cc9】

The CPSA defrole construct maps directly onto strand-space concepts.

CPSA Construct Strand-Space Concept
defrole Strand Template
trace Ordered Event Sequence
send Positive Node
recv Negative Node
Instantiated Role Strand
Strand Collection Skeleton
Realized Skeleton Shape

A role is not itself a strand. Instead, it acts as a template from which strands are generated during analysis. Multiple strands may therefore be instantiated from a single role definition. 【1-65b48d】【2-cf2cc9】

The sequence of events contained in a role corresponds to the sequence of nodes that characterize an execution strand. Each transmission event corresponds to a positive node, and each reception event corresponds to a negative node. 【1-65b48d】

Authentication arguments frequently depend on the relationships among strands, the uniqueness of originating values, and causal ordering constraints among nodes. CPSA uses these concepts extensively when generating shapes and evaluating security goals. 【3-5768ef】【1-65b48d】

2.6 Abstract Syntax

General form:

(defrole role-name
  declarations
  role-body)

Canonical structure:

(defrole initiator
  (vars
    (a b name)
    (n text))

  (trace
    (send ...)
    (recv ...))

  (uniq-orig n)
  (non-orig (privk a)))

This structure reflects the standard CPSA role definition format in which variable declarations provide role parameters and the trace defines participant behavior. Origination assumptions and non-origination assumptions constrain the security properties considered during analysis. 【1-65b48d】【2-cf2cc9】

2.7 English Description of Syntax

A defrole declaration:

  1. Begins with the keyword defrole.
  2. Specifies a unique role identifier.
  3. Declares role-local variables using one or more vars forms.
  4. Defines behavior through exactly one trace.
  5. May declare uniquely originating values.
  6. May declare non-originating values.
  7. May declare facts.
  8. May include additional CPSA-supported annotations.

Collectively, these declarations define the behavior expected of an honest participant executing the protocol. 【1-65b48d】【2-cf2cc9】

2.8 Syntax Components

2.8.1 Role Name

The role name uniquely identifies the role within a protocol definition. Each role name serves as a symbolic identifier that can later be referenced by strands, skeletons, goals, and analysis constructs. 【2-cf2cc9】【1-65b48d】

Example:

(defrole initiator
 ...)

Constraints

  • Must be unique within a protocol.
  • Must be a valid CPSA identifier.
  • Must not conflict with another role in the same protocol.

Metamodel Mapping

defrole name → Role.name

2.8.2 Variable Declarations

Variables define symbolic parameters used within traces and message terms. CPSA employs a many-sorted message algebra in which each variable is associated with a declared sort. 【2-cf2cc9】【1-65b48d】

Example:

(vars
  (a b name)
  (n text)
  (k skey))

Semantics

Variables represent unknown protocol values that become bound during strand instantiation and analysis. Sort declarations restrict the kinds of values that may be substituted for variables. 【2-cf2cc9】【1-65b48d】

Semantic Mapping

vars → Variable
name → Sort
text → Sort
skey → Sort

UML Classes

  • Variable
  • Sort

Example Attribution

The style of variable declaration shown above follows the conventions established throughout CPSA documentation and examples. Principal identities are typically represented using the name sort, fresh values using the text sort, and cryptographic keys using key-related sorts such as skey. 【2-cf2cc9】【3-5768ef】

2.8.3 Trace Declaration

A role contains exactly one trace.

Example:

(trace
  (send m1)
  (recv m2)
  (send m3))

A trace defines the ordered sequence of communication events associated with a role. Event ordering is semantically significant because strand-space reasoning depends on the causal ordering of transmissions and receptions. 【1-65b48d】【2-cf2cc9】

Semantic Mapping

trace → Trace

Constraints

  • Trace ordering is significant.
  • Event order is immutable.
  • Events are indexed by position.
  • Every trace contains at least one event.

Example Attribution

This pattern reflects the standard CPSA view of protocol behavior as an ordered sequence of communication events occurring along a strand. Similar structures appear throughout CPSA examples and the strand-space literature. 【1-65b48d】【2-cf2cc9】

2.8.4 Send Events

Example:

(send (enc n (pubk b)))

A send event represents transmission of a message by a protocol participant. Within strand-space terminology, a transmission event corresponds to a positive node within a strand. 【1-65b48d】

Meaning

The participant transmits the specified message onto the communication medium.

Metamodel Mapping

send → SendEvent

Processing Semantics

During analysis, send events contribute information that may explain receptions observed elsewhere in a skeleton. CPSA attempts to determine what transmissions must exist to satisfy observed communication patterns. 【3-5768ef】【2-cf2cc9】

2.8.5 Receive Events

Example:

(recv (enc n (pubk a)))

A receive event represents reception of a message by a protocol participant. Within strand-space terminology, a reception event corresponds to a negative node within a strand. 【1-65b48d】

Meaning

The participant expects reception of a message compatible with the specified message pattern.

Metamodel Mapping

recv → ReceiveEvent

Processing Semantics

Receive events frequently drive CPSA augmentation because the analyzer must determine what preceding behavior could account for the observed reception. 【3-5768ef】【2-cf2cc9】

2.8.6 uniq-orig

The uniq-orig construct specifies that one or more terms originate uniquely within honest protocol behavior. Unique origination assumptions are central to CPSA authentication reasoning and are commonly used to model freshness assumptions associated with nonces, session identifiers, and newly generated values. 【1-057dd3】【2-487b95】

Example:

(uniq-orig n)

Meaning

The specified term originates at exactly one location within honest protocol execution.

Typical Uses

  • Nonces
  • Session identifiers
  • Transaction identifiers
  • Fresh cryptographic material

Metamodel Mapping

uniq-orig → OriginationConstraint

Example Attribution

The use of uniquely originating nonces is a standard modeling practice throughout CPSA documentation and strand-space analyses because authentication arguments frequently depend on proving that a value has a single honest source. 【1-057dd3】【2-487b95】

2.8.7 non-orig

The non-orig construct identifies terms assumed not to originate within honest protocol behavior. Such values are treated as uncompromised inputs to the analysis and are frequently used to model protected long-term secrets. 【1-057dd3】【2-487b95】

Example:

(non-orig (privk a))

Meaning

The specified value is assumed not to originate from any honest protocol participant during the execution under consideration.

Typical Uses

  • Long-term private keys
  • Shared master secrets
  • Root credentials
  • Protected security parameters

Metamodel Mapping

non-orig → NonOriginationConstraint

Example Attribution

Modeling private keys as non-originating values is a common CPSA practice because authentication and secrecy analyses often assume uncompromised cryptographic credentials. 【1-057dd3】【2-487b95】

2.8.8 Facts

Facts provide analysis annotations that extend protocol reasoning beyond pure message exchange. Facts are especially important in CPSA models involving state reasoning, trusted relationships, authorization constraints, and protocol-specific assumptions. 【3-337807】【1-057dd3】

Example:

(facts
  (trusted a)
  (registered b))

Semantic Mapping

facts → Fact

UML Classes

  • Fact

Example Attribution

The use of facts extends the original strand-space formalism and supports richer protocol-analysis scenarios including state-based reasoning and rule processing. 【3-337807】【1-057dd3】

2.14 CPSA Processing Semantics

During protocol loading, CPSA:

  1. Parses the role definition. 【2-487b95】
  2. Creates internal variable representations. 【2-487b95】
  3. Builds trace event structures. 【2-487b95】
  4. Validates sort consistency. 【2-487b95】
  5. Registers uniqueness assumptions. 【2-487b95】
  6. Registers non-origination assumptions. 【2-487b95】
  7. Associates the role with its enclosing protocol. 【2-487b95】

During analysis, CPSA:

  1. Instantiates roles as strands. 【1-057dd3】【2-487b95】
  2. Performs term substitutions. 【2-487b95】
  3. Evaluates origination assumptions. 【1-057dd3】【2-487b95】
  4. Applies protocol rules. 【1-057dd3】
  5. Constructs and transforms skeletons. 【2-487b95】【4-426c98】
  6. Performs augmentation and reduction operations. 【2-487b95】
  7. Computes protocol shapes. 【4-426c98】【2-487b95】
  8. Identifies realized executions. 【1-057dd3】

One of CPSA's primary goals is the enumeration of all essentially distinct shapes compatible with an initial problem description. Authentication properties, secrecy properties, attacks, and anomalies can frequently be determined from these shapes. 【4-426c98】【2-487b95】

2.15 Common Modeling Mistakes

Mistake 1: Omitting Variable Declarations

Incorrect:

(send (enc n (pubk b)))

without declaring n or b.

Consequence

Undefined variables prevent proper interpretation and analysis.

Mistake 2: Incorrect Event Ordering

Placing events in an order inconsistent with the protocol design.

Consequence

Strand-space reasoning may produce unintended or misleading results. 【1-057dd3】【2-487b95】

Mistake 3: Missing uniq-orig Assumptions

Fresh values used without uniqueness assumptions.

Consequence

Authentication arguments may fail because freshness cannot be established. 【1-057dd3】【2-487b95】

Mistake 4: Misuse of non-orig

Declaring values as non-originating when protocol participants legitimately generate them.

Consequence

The model no longer accurately reflects protocol semantics.

Mistake 5: Role Duplication

Creating multiple roles that express identical behavior.

Consequence

Unnecessary complexity and reduced model clarity.

2.19 Complete Example

Needham-Schroeder Public-Key Protocol Lineage Example

(defrole initiator
  (vars
    (a b name)
    (na text))

  (trace
    (send (enc na a (pubk b)))
    (recv (enc na nb (pubk a)))
    (send (enc nb (pubk b))))

  (uniq-orig na)
  (non-orig (privk a))
  (non-orig (privk b)))

Example Attribution

This example is derived from the Needham-Schroeder Public-Key Protocol introduced by Needham and Schroeder and follows a modeling style commonly used in strand-space and CPSA analyses. The example has been simplified for explanatory purposes while preserving the essential structure of the initiator role. 【1-057dd3】

The modeling style used in this example is consistent with CPSA protocol examples, particularly the representation of principals as variables, explicit nonce generation, and long-term key protection assumptions. 【4-426c98】【2-487b95】

Interpretation

The variable a represents the initiator principal, while b represents the intended responder. Variables are declared using CPSA's many-sorted message algebra and parameterize the role definition. 【1-057dd3】【2-487b95】

The nonce na is introduced as a fresh value and is declared uniquely originating through the uniq-orig declaration. Unique origination assumptions support freshness reasoning and authentication analysis. 【1-057dd3】【2-487b95】

The trace consists of three ordered communication events. Event ordering is semantically significant because strand-space analysis depends on causal relationships among transmission and reception nodes. 【1-057dd3】【2-487b95】

The declarations:

(non-orig (privk a))
(non-orig (privk b))

assert that the long-term private keys remain uncompromised throughout the analysis. Such assumptions are common in authentication and secrecy studies conducted with CPSA. 【1-057dd3】【2-487b95】
